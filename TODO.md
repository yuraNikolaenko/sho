## Pending / Backlog

- [ ] **Баг: вибір рядка в таблиці Lines не скролить превью до цього рядка.**

  **Симптом:** документ містить кілька рядків з матчами, у нижній панелі Lines показано всі. Клік по будь-якому рядку (2-му, 3-му, N-му) — превью залишається на першому `<mark id="m0">`, виділення/скрол не змінюються. Очікувано: при кліку рядка в Lines превью має проскролити саме до того матчу, який відповідає цьому рядку (і бажано візуально виділити саме його — наприклад `m.current` клас).

  **Причина (гіпотеза):** наразі `DocxPreviewService.Render` генерує статичний HTML і JS який один раз робить `scrollIntoView('#m0')` на `DOMContentLoaded`. Селекшен у Lines-таблиці не ретранслюється у WebView2 — немає каналу `host → page` для "перейти до N-го матча". Кожна зміна вибору в Lines просто переносить TextBlock з номером файла, але WebView не отримує команди.

  **Що зробити:**
  1. У JS-частині `DocxPreviewService` додати глобальну функцію `window.shoJumpToMatch(index)` яка прибирає клас `current` з усіх `<mark>`, ставить його на `#m{index}`, і робить `scrollIntoView({block:'center'})`.
  2. Додати CSS для `.current` (контрастна рамка / насиченіший фон), щоб користувач бачив _який саме_ матч активний.
  3. Маппінг "рядок у Lines → індекс mark у HTML" — на момент генерації превью передавати в `DocxPreviewService.Render` упорядкований список діапазонів матчів (start/length у raw text). JS-обгортка `<mark>` йде по тих самих діапазонах у тому ж порядку, тож індекс рядка в Lines == `id="m{idx}"`. Якщо порядок матчів у raw text != порядок у HTML (Mammoth може реорганізувати inline-структуру) — зберігати в кожному `<mark>` `data-line="{N}"` і шукати по ньому.
  4. У [MainWindow.xaml.cs](src/Sho.App/MainWindow.xaml.cs) на `LinesGrid.SelectionChanged` (або відповідному обробнику) — викликати `WebView.CoreWebView2.ExecuteScriptAsync($"shoJumpToMatch({index})")`. `index` беремо як позицію вибраного `SearchHit` у списку матчів _саме цього файла_ (не глобально по всім файлам).
  5. Якщо вибраний рядок з іншого файла, ніж зараз показано — спочатку перерендерити превью (як зараз), а після `NavigationCompleted` викликати `shoJumpToMatch`. Зберігати pending-index у полі вікна, очищати після виконання.

  **Файли:**
  - [src/Sho.App/Services/DocxPreviewService.cs](src/Sho.App/Services/DocxPreviewService.cs) — JS API + CSS `.current` + `data-line` атрибути.
  - [src/Sho.App/MainWindow.xaml.cs](src/Sho.App/MainWindow.xaml.cs) — обробник `SelectionChanged` Lines-таблиці, виклик `ExecuteScriptAsync`, pending-index після навігації.

- [ ] **Баг: превью позиціонується на не-першому реальному збігу запиту.**

  **Симптом:** запит `НІКОЛАЄНКА Юрія Вікторовича` — пошук повернув документи коректно. При виборі документа в DOCX-превью підсвічування і `scrollIntoView` стрибнули на перше входження одного зі слів запиту (`Вікторовича` у фразі типу "...Іванова Петра Вікторовича..."), а не на фактичну згадку шуканої особи `Ніколаєнка Юрія Вікторовича`.

  **Причина (гіпотеза):** `DocxPreviewService.Render` отримує список окремих термів (`["ніколаєнка", "юрія", "вікторовича"]`) і `<script>` всередині HTML wraps кожне входження кожного терма незалежно у `<mark id="m0..N">`, після чого `scrollIntoView('#m0')`. Тобто jump іде на саме перше попадання _будь-якого_ з трьох слів у документі, а не на місце, де всі три слова стоять поруч (фактичне згадування особи). Для багатотермних запитів треба позиціонуватись на найкращий "кластер" — діапазон де знайдено максимум термів у мінімальному вікні (наприклад ≤ 50 символів), або хоча б на перше входження найрідкіснішого терма (`ніколаєнка`), а не на перше входження першого терма.

  **Кроки відтворення:** індекс по теці з наказами, де у багатьох документах згадуються різні особи з по-батькові "Вікторович". Запит `Ніколаєнка Юрія Вікторовича` → клік на документ де реально є Ніколаєнко Юрій Вікторович, але перед цим у тексті ідуть інші особи з "Вікторович". Превью скролиться на чужого "Вікторовича".

  **Що спробувати:**
  1. У `DocxPreviewService.Render` (і відповідному JS) — після обгортання `<mark>` знайти кластер: вікно тексту мінімальної довжини, що містить найбільшу кількість _різних_ термів запиту. `scrollIntoView` робити на перший `<mark>` всередині цього вікна.
  2. Якщо кластерна логіка важка — мінімальний фікс: сортувати терми за рідкістю (кількість входжень у документі ASC) і робити `scrollIntoView` на перший `<mark>` найрідкіснішого терма. Для прізвища це майже завжди дасть правильне місце.
  3. Перевірити, чи `MorphologicalLineMatcher` уже повертає кластерні діапазони для Lines-панелі — якщо так, можна передати точний `(start, length)` найкращої лінії в превью і скролити саме туди.

  **Файли:**
  - [src/Sho.App/Services/DocxPreviewService.cs](src/Sho.App/Services/DocxPreviewService.cs) — генерація HTML + JS, логіка `scrollIntoView`.
  - [src/Sho.Search/MorphologicalLineMatcher.cs](src/Sho.Search/MorphologicalLineMatcher.cs) — можливо, додати метод "найкращий діапазон" для документа.
  - [src/Sho.App/MainWindow.xaml.cs](src/Sho.App/MainWindow.xaml.cs) — точка виклику `DocxPreviewService.Render`, передати best-range якщо буде.

  **Acceptance:**
  - Запит `Ніколаєнка Юрія Вікторовича` на документі де ця особа згадана після інших "Вікторовичів" — превью скролиться саме на `Ніколаєнка...`, не на чужого `Вікторовича`.
  - Однотермний запит — поведінка не змінилась (скрол на перше входження).
  - Тест на штучному документі: 5 чужих "Вікторовичів" + 1 кластер з трьох термів → cursor на кластер.
